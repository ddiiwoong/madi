# 블록 편집기 설계 — 표를 격자로 편집하기 위한 구조

이 문서는 Md의 편집기를 **블록 기반**으로 다시 세우는 설계다. 목적은 하나다:
마크다운 표를 실제 격자로, 셀 단위로 편집하는 것. 지금 구조로는 안 되고, 왜 안 되는지와
무엇으로 바꿔야 하는지를 적는다.

## 1. 지금 구조가 막히는 지점

현재 편집기는 `NSTextStorage` 하나에 마크다운 원문을 담고, 그것을 서식 있는 문서처럼
그린다(`Sources/Madi/Editor/MarkdownEditorView.swift`). 제목·굵게·
코드·링크는 글자 속성으로 표현되고, 마커는 글리프를 제어문자로 바꿔 폭 0으로 만든다.

표가 막히는 이유는 성능이나 구현 난이도가 아니라 **텍스트 시스템의 모델 자체**다.
TextKit의 레이아웃 단위는 "줄"이고, 한 문자 범위는 한 줄에 속한다. 2차원 격자는 셀마다
독립적인 줄 흐름·너비·수직 정렬을 가져야 하는데, 이것을 하나의 선형 텍스트 흐름으로
표현할 방법이 없다. `NSTextTable`(TextKit 1의 표 지원)이 존재하지만 이것은 **RTF 문서용**
이고, 셀 안의 텍스트가 같은 text storage를 공유하기 때문에 "셀 단위 캐럿 이동", "탭으로
다음 셀", "열 너비 드래그", "행 삽입"을 구현하면 범위 계산이 전부 전역 오프셋 산술이 된다.
한 셀을 고치면 뒤따르는 모든 셀의 오프셋이 밀린다.

Mark.app이 이것을 공짜로 얻는 이유는 WKWebView 안에서 ProseMirror를 쓰기 때문이다.
ProseMirror의 문서는 선형 텍스트가 아니라 **노드 트리**이고, 표는 `table > row > cell`
노드이며 각 셀이 자기 안의 텍스트 흐름을 가진다. 접근성 트리를 읽어 보면 그것이 그대로
보인다 — `table` → `row` → `cell`, 전부 편집 가능.

즉 선택지는 "텍스트 시스템 안에서 표를 흉내내기"가 아니라 **문서 모델을 트리로 바꾸기**다.

## 2. 후보 세 가지

| 안 | 내용 | 장점 | 치명적 단점 |
|---|---|---|---|
| A. WKWebView + ProseMirror | Mark과 같은 길 | 표·이미지·중첩이 즉시 해결 | 네이티브가 아니게 된다. 사용자 요구와 정면 충돌 |
| B. `NSTextTable` 확장 | TextKit 1의 표 기능을 쓴다 | 추가 레이아웃 코드 없음 | 셀이 전역 오프셋을 공유 → 편집마다 범위 재계산. 마크다운 왕복이 사실상 불가능 |
| C. 블록 리스트 + 블록별 뷰 | 문서를 블록 배열로 두고 각 블록이 자기 뷰를 가진다 | 네이티브 유지, 표는 진짜 격자, 블록마다 최적 뷰 | 선택·되돌리기·캐럿 이동을 직접 조율해야 한다 |

**C를 택한다.** A는 요구사항을 배반하고, B는 왕복 충실도를 포기해야 한다.

## 3. 모델

문서는 블록의 배열이다. 각 블록은 안정적인 식별자를 갖고, 자기 원문 조각을 들고 있다.

```swift
struct BlockID: Hashable { let raw: UUID }

enum BlockKind {
    case paragraph        // 문단, 제목, 인용, 목록 — 텍스트 흐름 하나
    case heading(level: Int)
    case quote
    case list(ordered: Bool)
    case codeBlock(language: String?)
    case table(TableModel)
    case thematicBreak
    case image(url: String, alt: String)
    case html(raw: String)        // 파서가 모르는 것은 원문째로 보존
}

struct Block: Identifiable {
    let id: BlockID
    var kind: BlockKind
    /// 이 블록을 만든 원문. 파서가 모델링하지 못한 구문은 여기서 그대로 복원된다.
    var sourceSlice: String
}

struct TableModel {
    var alignments: [ColumnAlignment]
    var rows: [[String]]          // rows[0]이 헤더
}

struct BlockDocument {
    var frontMatter: FrontMatter?   // 이미 구현되어 있다
    var blocks: [Block]
}
```

핵심 규칙 하나: **파서가 이해하지 못한 블록은 `sourceSlice`를 그대로 다시 쓴다.**
front matter에서 이미 택한 원칙과 같다(`Sources/Madi/Core/FrontMatter.swift`).
재직렬화는 모델링한 블록에만 적용한다. 그렇지 않으면 저장할 때마다 사용자의 파일이
조용히 다시 쓰인다.

## 4. 렌더링

블록마다 전용 뷰를 두고, 수직으로 쌓는다.

```
BlockContainerView (NSView, 커스텀 레이아웃)
├── ParagraphBlockView   : NSTextView 하나 (지금의 스타일러를 그대로 재사용)
├── CodeBlockView        : NSTextView (모노스페이스, 마커 숨김 없음)
├── TableBlockView       : 셀마다 NSTextField/NSTextView를 둔 격자
├── ImageBlockView       : NSImageView + 대체 텍스트 편집
└── RuleBlockView        : 선 하나
```

`NSStackView`는 쓰지 않는다. 이미 이 세션에서 겪었듯 내재 크기를 가진 자식을 늘려 주지
않아 폭 제약을 따로 걸어야 하고, 수백 블록 문서에서 전부 레이아웃을 들고 있는 비용이 크다.
대신 **보이는 범위만 뷰를 만드는** 커스텀 레이아웃을 쓴다(`NSScrollView` 안에서 가시
영역을 계산해 블록 뷰를 재사용). 이것이 긴 문서에서 지금 구조보다 오히려 빨라지는 지점이다.

지금의 스타일러(`MarkdownStyler`)는 **문단 블록 안에서 그대로 쓴다.** 제목·굵게·인라인
코드·링크·마커 숨김은 블록 하나 안의 선형 텍스트 문제이고, 그 부분은 이미 동작한다.
버리는 것이 아니라 적용 범위가 블록 하나로 좁아진다.

## 5. 어려운 문제 다섯

이것이 이 작업의 실체다. 표를 그리는 것은 쉽고, 아래가 전부다.

**5.1 블록을 넘는 선택.** 한 문단 중간에서 드래그를 시작해 표 셀에서 끝나는 선택을
표현해야 한다. 각 블록 뷰가 자기 `NSTextView`를 가지면 first responder가 하나뿐이라
걸쳐 있는 선택이 자연히 표현되지 않는다. 설계: `SelectionCoordinator`가
`(startBlock, startOffset) → (endBlock, endOffset)`를 들고, 중간 블록은 "전체 선택"
상태로 자기 뷰에 그린다. 복사는 코디네이터가 블록들을 순회해 마크다운을 조립한다.

**5.2 되돌리기.** `NSTextView`마다 자기 `NSUndoManager`를 가지면 ⌘Z가 방금 고친 셀이
아니라 엉뚱한 블록을 되돌린다. 설계: 블록 뷰들의 undo를 모두 끄고
**문서 레벨 `NSUndoManager` 하나**에 등록한다. 등록 단위는 "블록 N의 텍스트가 A→B",
"블록 N 삽입/삭제", "표 M의 셀 (r,c)가 A→B"처럼 모델 연산으로 둔다.

**5.3 캐럿 이동.** 문단 마지막 줄에서 ↓를 누르면 다음 블록의 첫 줄로, 표 셀에서 Tab은
다음 셀로, 마지막 셀에서 Tab은 새 행. 설계: 각 블록 뷰가 "내 경계를 넘었다"를 코디네이터에
알리고(`didMoveCaretBeyond(.bottom)`), 코디네이터가 다음 블록의 first responder를 잡고
수평 위치를 보존해 캐럿을 놓는다.

**5.4 입력기(IME).** 한글 조합 중에 블록이 바뀌면 조합이 깨진다. 조합 중에는 블록 경계
이동과 재레이아웃을 막아야 한다(`NSTextInputClient.hasMarkedText`를 코디네이터가 확인).
이것은 한국어 사용자에게 가장 먼저 티가 나는 결함이므로 Phase 1부터 테스트에 넣는다.

**5.5 접근성.** 지금은 `NSTextView` 하나라서 접근성이 공짜다. 블록으로 쪼개면 표가
`AXTable`/`AXRow`/`AXCell`로 올바르게 노출되는지 직접 확인해야 한다 — Mark이 그렇게
노출하고 있으니 같은 기준을 쓴다.

## 6. 직렬화 경계

```
파일 → FrontMatter.parse → BlockParser → BlockDocument
BlockDocument → BlockSerializer → 파일
```

불변식 하나를 테스트로 못박는다: **파싱 후 바로 직렬화하면 원본과 바이트가 같다.**
표의 열 너비 정렬(`| --- |`의 하이픈 개수)처럼 의미가 없는 차이도 보존 대상이다 —
저장이 diff를 만들면 git을 쓰는 사용자가 즉시 싫어한다. 실제 문서들을 코퍼스로 두고
왕복을 돌린다.

## 7. 단계 — 각 단계가 그 자체로 출하 가능해야 한다

| 단계 | 내용 | 끝났다고 말할 조건 |
|---|---|---|
| 0 | `BlockParser` / `BlockSerializer`와 왕복 테스트. UI 변경 없음 | 실제 문서 코퍼스에서 왕복이 바이트 동일 |
| 1 | 문단 블록만 블록 컨테이너로 렌더. 표는 아직 텍스트 | 지금과 동작이 같다. 한글 조합·되돌리기·블록 넘는 선택이 깨지지 않는다 |
| 2 | `TableBlockView` 읽기 전용 격자 | 표가 격자로 보인다. 편집은 코드 보기에서 |
| 3 | 표 셀 편집, Tab 이동, 행·열 추가/삭제 | 셀 편집이 모델에 반영되고 왕복이 유지된다 |
| 4 | 이미지 블록 인라인 표시 | 이미지가 보이고 대체 텍스트를 고칠 수 있다 |

단계 1이 전체 위험의 대부분이다. 거기서 한글 조합이나 되돌리기가 무너지면 2~4는 의미가
없다. **단계 1을 넘기지 못하면 멈추고 현재 구조로 되돌리는 것이 정답이다** — 표가 격자로
보이는 대가로 한글 입력이 불안정한 에디터는 거래가 성립하지 않는다.

## 8. 비용과 빠질 구멍

단계 0~1이 이 작업의 절반이고, 혼자 집중해서 며칠 단위가 아니라 주 단위다. 5.1~5.4는
각각 독립적으로 까다롭고, 특히 되돌리기와 입력기는 "거의 동작한다"가 곧 버그 리포트다.

빠질 구멍으로 미리 적어 둔다:

- **표만 보고 시작하지 말 것.** 표는 단계 2~3이고, 그 앞의 단계 0~1이 진짜 작업이다.
- `NSTextView`를 블록마다 만드는 비용은 생각보다 크다. 가시 영역 재사용 없이 500블록
  문서를 열면 체감된다. 단계 1에서 큰 실제 문서로 측정하고 넘어간다.
- 지금의 라이브 프리뷰(마커 숨김)를 버릴 이유가 없다. 블록 안에서 계속 쓴다.
- 현재 구조를 지우지 말 것. 단계 1이 실패했을 때 돌아올 곳이다.
